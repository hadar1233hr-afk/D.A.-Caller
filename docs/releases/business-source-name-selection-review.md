changes, production data admission, native activation or publication. The pending

`osm:node:5066707334`, source date 2023-10-26T19:50:14+00:00, already has clean
`name=Rena's House`. Its source `addr:city` is `Tel Aviv\u200e`; the constructed
address is `Simtat Beit HaBad 3 Tel Aviv\u200e`. The source report contains no
clean city or full-address alternative. Its raw BLOB hash is

Selecting another name cannot fix this row. Keep it withheld in this derivative.

exact-display contract. A future explicit policy might separately omit an unsafe
optional display field or construct a street/house-only display from original
components, while retaining the full raw source and explicit omission reasons;
that is a different reviewed projection and is not authorized by this review.

## The ten withheld phone rows

The ten source rows represent eight distinct UAN 1599 identities. Their national
forms round-trip to the same source E.164 identity in the retained phone review.
However the current native `normalizedPhone` and `phonePrefix` blindly prepend
`0` after `+972`, `00972` or bare `972`. A source value such as
`+9721599555535` becomes unsupported `01599555535`, whereas national `1599555535`
is accepted. This is a source/native formatting mismatch, not proof that the
source phone is invented, currently assigned or reachable.

A tool-only derivative could display/store the reviewed national form and retain
the exact E.164 source in provenance; national dialing/querying would fit the
existing reader contract. It would **not** fix international-alias queries: those
still search the wrong zero-prefixed identity. Full source-E.164/alias support
requires a reviewed native normalizer and query-prefix change, matching Python
contract updates and fresh actual-reader/emulator verification in a future
business-enabled source. It must not silently alter current 0.12.0 or the frozen
candidate. Keep all ten withheld in this name-selection-only profile.
