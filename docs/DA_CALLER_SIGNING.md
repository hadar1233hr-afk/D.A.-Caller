# חתימה קבועה ועדכונים של DA CALLER

מפתח חתימה הוא החותמת הפרטית של מפתח האפליקציה. המשתמש אינו אמור להכין אותו בעצמו. Android מאשר עדכון של התקנה קיימת רק כאשר החתימה תואמת, או כאשר שרשרת החלפת מפתחות תקפה נוצרה בעזרת המפתח הישן.

## ההתקנה הקיימת של beta.9

חתימת beta.9 שפורסמה היא `3d41dabd6e32a28ba6af2c57bb872fb3dfafa1f85a5c8523b72b54e4d8a32f56`. היא נוצרה בריצת CI זמנית. ארבעת תוצרי הריצה שנשמרו מכילים APK ודוחות בלבד; המטמון שמר רק קובצי Gradle ולא את `~/.android/debug.keystore`. המפתח המקומי היחיד שנמצא הוא בעל חתימה אחרת: `fb4a138563caff0c59a35327a8e2865c91fea72c6d28c667c56623b1ba9110fc`.

לכן עדכון ישיר של התקנת beta.9 הזאת **BLOCKED: המפתח הפרטי המקורי אינו זמין במסלולים שנבדקו**. הגדלת מספר הגרסה, החתמה במפתח חדש או יצירת שרשרת חתימה בלי המפתח הישן אינן פותרות זאת. אי אפשר לשחזר מפתח RSA פרטי מתוך APK או תעודה ציבורית.

**אין להסיר התקנה קיימת:** הסרה מוחקת את הארכיון וההגדרות הפרטיים. גיבוי ההגדרות הקיים אינו גיבוי הארכיון. הכלים החדשים להלן מונעים החלפת חתימה בגרסאות עתידיות; הם אינם מציגים את בעיית ההתקנה הישנה כפתורה.

## כלי ההכנה החד־פעמית

הכלי `scripts/da_caller_signing.py` נועד למפתח או לבעל המאגר, ולא לפעולה אוטומטית בזמן build. דרושים Python3, Java/keytool, וקבצים פרטיים מחוץ למאגר. פעולת `init` מסרבת לדרוס תיקייה או גיבוי קיימים; פעולות `verify` ו־`upload-secrets` לעולם אינן מייצרות מפתח חלופי.

```bash
python3 scripts/da_caller_signing.py init \
  --directory /workspace/private/da-caller-signing
```

הדוגמה משתמשת בנתיב פרטי בסביבת הפיתוח; במחשב הבעלים יש לבחור נתיב פרטי מתאים מחוץ לכל מאגר. נוצרים תיקייה בהרשאת0700, מפתח RSA3072 במאגר JKS, קובץ סיסמה אקראית וקובץ הוראות התאוששות עם הרשאות0600. הסיסמה מועברת ל־keytool באמצעות קובץ, ואינה נמצאת בארגומנטים או בפלט. הפלט מציג רק fingerprint ציבורי ומיקומי הקבצים.

ליד התיקייה נוצר `da-caller-signing-owner-backup.tar.gz` בהרשאת0600. הוא מכיל **גם מפתח פרטי וגם סיסמה**, ולכן יש לשמור אותו בגיבוי פרטי שבשליטת הבעלים. הוא אינו מיועד למאגר Git, ל־Release ציבורי, ל־Issue או לתוצר CI. `certificate.json` מכיל נתונים ציבוריים בלבד; רק אותו או את ה־fingerprint יש להעתיק למסמך ההצמדה במאגר לאחר סקירה.

אם יצירה נכשלת, אין לייצר מפתח חדש אוטומטית או למחוק את הקבצים שנוצרו. יש לשמור את התיקייה ולבדוק מה קרה. אם המפתח אבד בעתיד, build ופרסום חייבים להיכשל עד להחזרת המפתח מהגיבוי.

## אימות לפני כל build שמיועד להתקנה

```bash
python3 scripts/da_caller_signing.py verify \
  --directory /workspace/private/da-caller-signing \
  --expected-certificate PUBLIC_PINNED_SHA256 \
  --previous-certificate PREVIOUS_RELEASE_SHA256
```

כל fingerprint הוא64 ספרות הקסדצימליות, עם או בלי נקודתיים. כאשר מסופקת חתימת גרסה קודמת היא חייבת להתאים, אחרת הפעולה נכשלת לפני שימוש במפתח. אם לא סופקה, הפלט מציין במפורש שלא נבדקה תאימות לעדכון קודם. אין להציג מצב כזה כאימות עדכון של ההתקנה הישנה.

ה־CI חייב לקבל את אותו מפתח **לפני** בניית ה־APK שיותקן באמולטור. לאחר הבדיקות עליו לפרסם את אותו בינארי בדיוק ולוודא את חתימתו מול ה־fingerprint הקבוע. היעדר מפתח, סיסמה או הצמדה, או חתימה שונה מגרסה קודמת, חייבים לחסום פרסום; אין fallback למפתח debug אקראי. אין לשמור מפתח פרטי במטמון או בתוצרי Actions.

בדיקת התעודה של `verify` מאמתת את זהות התעודה ואת קיומה של רשומת מפתח פרטי. היא אינה מחליפה חתימת APK אמיתית: יכולת פענוח המפתח עם סיסמת המפתח נבדקת בפועל בשלב החתימה של הבנייה, ולאחריו נדרש `apksigner verify` על הקובץ שיופץ.

## הגדרת סודות GitHub בידי הבעלים

לאחר בדיקת המפתח והצמדת התעודה הציבורית, בעל הרשאה מתאים יכול להשתמש ב־GitHub CLI שכבר מחובר לחשבונו:

```bash
python3 scripts/da_caller_signing.py upload-secrets \
  --directory /workspace/private/da-caller-signing \
  --expected-certificate PUBLIC_PINNED_SHA256 \
  --repository hadar1233hr-afk/D.A.-Caller \
  --environment da-caller-release
```

הפקודה מגדירה רק `DA_CALLER_KEYSTORE_BASE64`,‏ `DA_CALLER_KEYSTORE_PASSWORD` ו־`DA_CALLER_CERT_SHA256`, באמצעות stdin ולא בארגומנטים. היא אינה מדפיסה ערכי סודות, אינה מתחברת לחשבון אחר ואינה עוקפת הרשאות או מדיניות רשת. אם ההרשאה אינה קיימת, אפשר להגדיר ידנית את אותם שלושה סודות במסך GitHub המתאים; אין להריץ login אוטומטי או להעביר את המפתח דרך קישור ציבורי. ב־CI יש להשתמש בסודות רק במסלול המאושר של המאגר המקורי, ולהשאיר הגנות סקירה מתאימות לסביבת הפרסום.

העלאת הסודות היא פעולה מפורשת של הבעלים, לא חלק מבדיקה מקומית או מפקודת `init`. שלושת הסודות נכתבים ברצף; אם פעולה נכשלת באמצע, אין לפרסם עד להגדרה ולהשוואה מוצלחות של כולם. אפשר להריץ שוב את ההעלאה עם אותו מפתח קיים; אין ליצור מפתח חלופי. קוד הכלי והבדיקות אינם יוצרים מפתח או מעלים סודות מעצמם.
